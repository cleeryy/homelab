title: Decommissioning
description: Procedure for retiring a service, guest, or node.
---

Deleting things is a skill, and this homelab has gotten good at it — the migration plan's resolved list is proof. Decommissioning has a procedure for the same reason provisioning does: a guest removed without cleaning its DNS, ingress, monitoring, and documentation entries leaves ghosts that confuse the next incident response. Retire things completely or not at all, take the final backup when data matters, and update the wiki in the same motion so the inventory stays honest. The checklists below read as numbered steps now, but the spirit is unchanged: every layer the service touched gets unwound, in an order that never strands a dependent.

## Service inside a Docker host

This is the lightest retirement, for a single containerised service living inside a shared Docker host's compose file. Because the host itself survives, the work is mostly editing and committing rather than deleting infrastructure, but the documentation step matters just as much — a service page that still describes a removed container is a trap for the next reader.

1. Stop the container in compose so it is no longer serving traffic.
2. Remove the service block from the compose file entirely.
3. Remove the volume if its data is not meant to be preserved.
4. Commit the compose change to Forgejo so the removal is versioned like any other change.
5. Update the matching service page under [Services](/services/core/reverse-proxy) to reflect that the service is gone.

Once the compose change is committed and the page updated, confirm the host still converges cleanly (no dangling references to the removed service) before considering the retirement done. A leftover network alias or volume reference is the classic way a clean removal turns into a confusing deploy failure weeks later.

## Standalone VM or LXC

A whole guest touches far more systems than a compose service, so its retirement is really a small dependency-removal project. The order is defensive: prove nothing depends on it first, cut its public face, preserve data if anyone might want it back, and only then stop and delete, finishing with the inventory so the maps match the territory.

1. Confirm that no other service depends on the guest by checking [Service placement](/architecture/service-placement).
2. Remove its ingress and DNS entries so nothing still routes toward it.
3. Take a final `vzdump` if its data must be preserved beyond the shutdown.
4. Stop the guest.
5. Remove the guest from Proxmox.
6. Remove the host from Beszel monitoring so it stops alerting (or absence-polluting) after deletion.
7. Update [Inventory](/inventory/virtual-machines) and [Service placement](/architecture/service-placement) to drop every mention of the retired guest.

The outro is the wiki diff itself: if inventory and placement no longer mention the guest, DNS and Caddy no longer route to it, and Beszel no longer watches for it, the decommission is complete. Anything left pointing at a deleted ID means the procedure was stopped one step early.

## Node (`pve2`, future)

Node removal is rare — `pve2` was ejected on 09/09/2026 and this section exists for the next time — and it is the one decommission where doing things out of order can strand storage or break cluster state. Treat the confirmation step as load-bearing rather than ceremonial, and keep the cluster procedure itself out of scope here by following the documented Proxmox flow for the actual eviction.

1. Confirm that no workloads, snapshots, or storage references still point at the node.
2. Remove the node from the cluster using the documented Proxmox procedure (out of scope here).
3. Remove the matching `<node>-storage` entry from `/etc/pve/storage.cfg`.
4. Update [Nodes](/inventory/nodes) so the cluster membership on paper matches reality.

Verify from a surviving node that storage config parses, guests list cleanly, and no reference to the removed node lingers in the cluster state. A stale storage entry is quiet until the exact moment someone tries to provision against it.

## Known gaps

No defined cooldown before reusing a VM/CT ID, and no standing rule for parked-versus-removed. The working convention is evident from the tables above — things linger stopped until someone decides — but writing the rule down would make each decision take seconds instead of a discussion. Until that rule exists, say explicitly in the migration plan whether a stopped guest is parked or pending removal, so stillness reads as a decision rather than forgetfulness.
