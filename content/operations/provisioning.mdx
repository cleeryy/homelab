---
title: Provisioning
description: Procedure for bringing a new VM, LXC, or Docker stack online.
---

Bringing up something new should feel routine, not adventurous. This procedure exists so the tenth deployment looks like the first: pick the right layer, take a free ID in the right range, wire DNS and ingress the same way every time, and leave the wiki updated behind you. Skip steps and the homelab accumulates exactly the kind of mystery this documentation was written to kill.

## Decide where it goes

- **Containerised app / website** → Dokploy on `obiwan` (`205`), exposed through Caddy. See [Dokploy](/operations/dokploy).
- **Application Docker stack (legacy pattern)** → an Ubuntu VM on the appropriate node, following the pattern used for Nextcloud/n8n/Servarr (Docker compose + `portainer` + `watchtower` + `beszel-agent`). Prefer Dokploy for anything new.
- **Single-purpose system service** → Proxmox LXC on `pve3` (production/management VLANs) unless it belongs with the legacy `pve1` stack.
- **Storage-adjacent workload** → coordinate with TrueNAS for dataset and share creation.
- **Lab / pre-production** → `pve3`, in a clearly separated namespace.

## Allocate the ID

ID ranges currently in use are documented in [Inventory > Virtual machines](/inventory/virtual-machines). Pick a free ID in the matching range.

## Provision the guest

### VM (Docker host)

- [ ] Create on the target node.
- [ ] OS: Ubuntu 24.04 LTS to stay consistent with the rest of the Docker hosts.
- [ ] Install Docker and the compose plugin.
- [ ] Install the `beszel-agent` container and register the host in Beszel.
- [ ] Install `portainer` and `watchtower` if the host pattern uses them.
- [ ] Drop the compose file under version control (Forgejo).

### LXC

- [ ] Create on the target node from a vetted template.
- [ ] Apply baseline configuration (timezone, networking, SSH).
- [ ] Add to Beszel monitoring if relevant.

## Wire it in

- [ ] If user-facing, add a Caddy route (see [Reverse proxy](/services/core/reverse-proxy)): public zone for user services, private `*.home.cleeryy.cloud` zone for admin UIs. Add Authentik `forward_auth` unless the route is deliberately public.
- [ ] If the service stores data, decide where the data volume lives (`local-lvm`, `pve1-storage`, TrueNAS dataset, `nas`).
- [ ] If the service has a backend (Postgres, Redis), confirm the backend exists or stand it up first.

## Document it

- [ ] Add or update the matching page under [Services](/services/core/reverse-proxy).
- [ ] Update the placement table in [Service placement](/architecture/service-placement).
- [ ] Update the inventory page for VMs or LXCs.

## Known gaps

There is no scripted path here — no Terraform, no Ansible, just the manual happy path above. That is a conscious scope choice for a two-node homelab, not an oversight; if provisioning ever becomes frequent enough to hurt, automation gets its own page.
