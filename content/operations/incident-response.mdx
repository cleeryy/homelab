title: Incident response

Something is broken. This page is the order of operations for that moment: figure out which layer failed, apply the smallest fix that restores service, then write down what happened so the next incident is shorter. It is deliberately mechanical — triage before treatment, treatment before postmortem — because under pressure humans skip steps, and skipped steps are how small outages become big ones. The constraints section is the cheat sheet: the three single points of failure that explain most homelab-wide symptoms.

## Triage

- [ ] Identify the affected layer: Proxmox host, VM/LXC, Docker container, or external dependency.
- [ ] Check Beszel for host and container-level state. Recent observations to expect as benign:
  - `gluetun` on `QBittorrent` may be unhealthy without taking the whole stack down.
  - `portainer` on `Nextcloud` may be in a restarting loop without taking Nextcloud itself down.
  - `jellyfin` memory usage can be high during transcoding.
- [ ] Locate the service on [Service placement](/architecture/service-placement) to know which node and which dependencies are involved.

## Mitigate

- [ ] Apply the smallest change that restores service: restart the container, restart the guest, or restart the host service.
- [ ] If WAN is lost: check OPNsense (VM `501` on `pve3`), then the `WAN_GW` / `AIRVPN_GW` gateway status.
- [ ] If ingress is lost: check `caddy` (`2010` on `pve3`, `10.1.20.10`) and the OPNsense NAT forwards for 80/443.
- [ ] If SSH is lost: check `warpgate` (`222`) and Authentik (`130`).
- [ ] If DNS is broken internally: check `technitium` (`553`) and Unbound on OPNsense.
- [ ] If storage is unreachable: check `truenas` (`127`) and the `nas`/`truenas` mounts on each affected node.

## Recover

- [ ] If a backup restore is needed, follow [Backup & restore](/operations/backup-restore).
- [ ] Validate end-to-end before declaring resolution. Beszel state is a fast smoke test, not a validation.

## Follow up

- [ ] Short postmortem: what happened, what was done, what changed.
- [ ] Update affected documentation (service page, architecture page, this page) so the next incident is shorter.

## Useful constraints

- Caddy (`2010`) is the single ingress. A `pve3` host outage takes ingress, WAN (OPNsense `501`), TrueNAS, and most platform LXCs down at once — triage in that order.
- TrueNAS lives on `pve3`. A `pve3` host outage takes the media stack and a large portion of storage with it.
- PBS (`578`) also lives on `pve3`: during a `pve3` outage, restores depend on a fresh PBS or the off-site copy.

## Known gaps

No severity levels, no on-call rotation, no notification path — incidents are handled by whoever notices, which for a homelab is honestly fine. If that ever stops being fine, severity definitions come first and tooling second.
