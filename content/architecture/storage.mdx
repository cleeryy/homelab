Last synced with live infrastructure: **September 2026**.

Storage here is a patchwork with a history: local disks for speed, a ZFS pool inherited from the infra node era, NFS shares for the things both nodes need, TrueNAS for the bulk, and a backup server that finally gave the whole thing a safety net. The tier table below is the mental model to keep — when provisioning asks "where does this volume live", the answer should always be one of these rows, never "wherever fits". Anything that does not fit the tiers is a sign the model needs updating, not an excuse for a one-off mount.

## Proxmox storage from `/etc/pve/storage.cfg`

The storage configuration below is reproduced from `/etc/pve/storage.cfg` and covers every pool both nodes can see. It is the authoritative list: if a pool is not in this table, Proxmox does not know about it.

| Storage ID | Type | Path / source | Nodes | Content |
|------------|------|---------------|-------|---------|
| `local` | Directory | `/var/lib/vz` | `pve1`, `pve3` | `backup`, `iso`, `vztmpl` |
| `local-lvm` | LVM-thin | local LVM | `pve1`, `pve3` | `images`, `rootdir` |
| `pve1-storage` | ZFS pool | local ZFS on `pve1` | `pve1` | Application data on the infra node |
| `nas` | NFS | `192.168.1.16:/data/pve` | `pve1`, `pve3` | `rootdir`, `iso`, `backup`, `images` (`prune-backups keep-all=1`) |
| `truenas` | NFS | `192.168.1.74:/mnt/raw/pve` | `pve1`, `pve3` | `rootdir`, `images` |
| `pbs` | Proxmox Backup Server | `10.1.50.78`, datastore `backupstore` | `pve1`, `pve3` | `backup` |

The `pve2-storage` entry is gone because `pve2` has been fully removed from the cluster, and `pve3` has no native ZFS pool on the host. Its persistent data therefore lives on `local-lvm`, on TrueNAS datasets, or on the shared NFS mounts, which means `pve3` depends on network-attached storage for everything that outlives a single container rebuild.

## TrueNAS VM

The bulk-data story belongs to a single VM. VM `127` named `truenas` runs on `pve3` with roughly 8.5 GB of RAM in use and multiple physical disks passed through, reachable at `192.168.1.74`. It exposes datasets over NFS at `/mnt/raw/pve`, which both nodes mount as the `truenas` storage, and it serves SMB shares to the LAN for clients that do not speak NFS. Dataset-level layout, snapshot schedule, and replication targets are not captured here, and this page will be extended once the TrueNAS configuration is exported, since guessing at dataset names would be worse than admitting the gap.

## Proxmox Backup Server

Backups are storage too, and their side of the configuration lives here while policy lives next door. LXC `578` named `pbs` runs on `pve3` at `10.1.50.78:8007` with the datastore `backupstore` of roughly 600 GB. It is declared as the `pbs` storage on both nodes using token authentication as `pve@pbs!pve` with DatastoreAdmin rights scoped to the datastore only. See [Backups](/architecture/backups) for schedules, retention, and off-site sync.

## Tier model

The tier model below is how the storage layer is used in practice, as opposed to how Proxmox lists its pools. Each tier answers a different durability question, from reboot-surviving root disks to off-host backups.

| Tier | Where it lives | What sits there |
|------|----------------|-----------------|
| Node-local system | `local`, `local-lvm` on each node | VM and CT root disks, ISOs, templates, local backups |
| Application data (infra) | `pve1-storage` (ZFS on `pve1`) | Persistent data for infra-side workloads |
| Application data (compute) | `local-lvm` on `pve3`, TrueNAS datasets | Persistent data for production workloads |
| Bulk / shared | TrueNAS datasets, `nas` | Media library, large archives, cross-node assets |
| Backup | `pbs` (`backupstore`), `nas` (legacy `vzdump` target) | See [Backups](/architecture/backups) |

The split between infra-side and compute-side application data mirrors the node asymmetry: databases and forge data rest on the ZFS pool of `pve1`, while production state rests on the LVM-thin pool and datasets attached to `pve3`. Bulk and backup tiers are the only ones both nodes share symmetrically.

## Known gaps

Nobody has written down the TrueNAS dataset layout with per-pool capacity, nor the usable capacity of `pve1-storage`, `pve3` `local-lvm`, and `nas`. Storage works today on tribal knowledge; a capacity table is what stands between "working" and "plannable".
