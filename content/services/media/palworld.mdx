Last synced with live infrastructure: **September 2026**.

Unlike everything else on this site, Palworld does not speak HTTP at all. Game clients talk raw UDP to dedicated ports that the firewall forwards straight to the container — Caddy never sees this traffic, and none of the usual HTTPS tooling applies. That also makes it the noisiest guest on the network: expect unsolicited scans on those ports within hours of opening them, and keep an eye on CrowdSec. The world saves live on local disk, so the only ritual that matters is snapshotting before every game update.

## Placement

The game server runs as LXC `4001` (`palworld`) on `pve3` on the production VLAN at `10.1.20.143`, with 32 GB of RAM allocated — by far the most memory-hungry guest in this section.

## Ingress

There is no Caddy involvement here: dedicated game ports arrive via OPNsense NAT, all UDP toward `10.1.20.143`, on `8211`, `8212`, and `27015`. Source-IP restriction is recommended but not confirmed in place, so treat the ports as internet-visible until proven otherwise.

## Dependencies

Save data lives on the LXC disk and is covered by the general PBS job. The save-restore procedure itself is not documented here, which is the gap that would hurt on the evening it matters.

## Failure impact

A `pve3` outage takes the game server down with the production VLAN. Worlds persist on disk through the outage, so the failure mode is interrupted play rather than lost progress — provided the saves are intact.

## Operational notes

Game servers attract unsolicited WAN traffic, so OPNsense and CrowdSec logs deserve a glance after any player-slot change. Updates wipe no data in the standard layout, but snapshot before updating anyway — cheap insurance against patch-day surprises.

## Known gaps

Nobody has drilled the save-data restore, source-IP restriction is unconfirmed, and the update procedure lives in someone's head. For a game server that is fine — until the evening thirty players lose a world. An hour of documentation buys a lot of goodwill.
