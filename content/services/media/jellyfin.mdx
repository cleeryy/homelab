Jellyfin is the cinema: the media library, collected by the Servarr stack and downloaded by qBittorrent, ends up watchable here on every screen in the house. Playback of finished downloads is the resilient part of the whole media chain — even if the indexers, the VPN, and the download client all die at once, movie night survives on what is already on disk. The fragile parts are the catalog metadata and the transcoder's appetite for RAM, in that order.

## Placement

- VM `300` `ubuntu-jelly` on `pve3`.
- Beszel label `Jelly`, IP `192.168.1.31`.

## Docker containers

| Container | Function |
|-----------|----------|
| `jellyfin` | Jellyfin media server |
| `seerr` | Request management (Jellyseerr / Overseerr family) |
| `beszel-agent` | Monitoring agent |

## Ingress

- `jellyfin.cleeryy.cloud` (alias `jelly.cleeryy.cloud`) → Caddy → `192.168.1.31:8096`.
- Requests: `jellyseerr.cleeryy.cloud` → Caddy → `192.168.1.31:5055`.

## Dependencies

- The media library is expected to live on TrueNAS datasets and to be mounted into the Jellyfin container. The exact mount path is **not captured here**.
- The media catalog is filled by the Servarr host (`301`), which writes to the same shared library.

## Operational notes

- `jellyfin` was reported as using a large amount of memory at the last observation. Transient.

## Failure impact

- A `pve3` outage takes Jellyfin, the Servarr stack, and qBittorrent down at the same time. TrueNAS, which sits on the same node, is also affected.
- Catalog continuity depends on Jellyfin's metadata volume, not on the media files themselves.

## Known gaps

The library mount path, the transcoder setup, and the catalog backup procedure are all unconfirmed — in other words, everything that would matter on rebuild day. The media files themselves are replaceable; the metadata volume is the part worth documenting.
