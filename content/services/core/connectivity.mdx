Last synced with live infrastructure: **September 2026**. All three terminate on OPNsense (VM `501`).

Three different networks answer three different questions. NetBird is the always-on management mesh: how do I reach the firewall and key hosts even when DNS or the ISP path is having a bad day. AirVPN is the privacy egress: how does selected VLAN traffic leave for the internet without carrying the home IP, and with a guarantee it never leaks onto clearnet if the tunnel drops. WireGuard road-warrior is the personal on-ramp: how does a laptop or phone join the homelab network directly. All three terminate on OPNsense, which makes the firewall the single place where remote-access policy lives — and the single box whose backup actually matters for connectivity.

## NetBird mesh

NetBird is the always-on management mesh, there so the firewall and key hosts stay reachable even when the ISP-facing path or local DNS is degraded. The firewall participates as a full peer with a stable mesh address, and direct plus relayed connections were both observed at the last snapshot. Static-port outbound NAT and a logged WAN rule keep peer-to-peer traffic flowing.

| Setting | Value |
|---------|-------|
| OPNsense interface | `wt0`, `100.121.135.95/16` |
| Plugin | `os-netbird` 1.3_3 |
| Peers | 7 online at last observation (relay + direct: production hosts, `pve1`, VPS) |
| WAN rule | Allow NetBird P2P `udp/51825` (logged) |
| Outbound NAT | Static-port mapping for NetBird traffic |

## AirVPN privacy egress

Selected VLAN traffic leaves for the internet through an AirVPN WireGuard tunnel so it never carries the home IP. The tunnel holds a stable exit address with a gateway that is monitored as online, and policy routing pushes the `INTERNAL` group through it. If the tunnel drops, a kill-switch block rule beneath the policy stops the affected traffic rather than letting it leak to WAN. Credentials live in the OPNsense configuration backup and are not reproduced here.

| Setting | Value |
|---------|-------|
| OPNsense interface | `wg1` (`AirVPN-NL3`), `10.130.184.82/32` + IPv6 ULA |
| Peer | `AirVPN-NL3-peer`, online, 15 s keepalive (~14 GB RX / ~353 GB TX lifetime at last observation) |
| Gateway | `AIRVPN_GW` (`10.128.0.1`), online |
| Policy | `INTERNAL` group → gateway `AIRVPN_GW`, with a **kill-switch** block rule beneath |

## WireGuard road-warrior

Personal devices join the homelab directly through a WireGuard server on OPNsense, getting addresses on their own `/24` with public DNS pushed to them. Three peers are provisioned but all showed offline at the last observation, which suggests dormant laptops and phones rather than a broken server. A logged WAN rule permits the handshake port, and keys live in the OPNsense configuration backup rather than here.

| Setting | Value |
|---------|-------|
| OPNsense interface | `wg0`, server `10.1.90.1/24`, listen `udp/51920` on WAN |
| Peers | `m4-air` (`.90.3`), `iphone15` (`.90.2`), `windaube` (`.90.4`) — all offline at last observation |
| Pushed DNS | `94.140.14.14`, `94.140.15.15` (AdGuard public) |

## Cloudflare tunnels

Cloudflare tunnels provide a fourth path that is about publishing, not about joining: selected services get public URLs without inbound firewall rules. That egress runs from `cloudflared` (LXC `103`, `pve1`) and `cloudflared-opnsense` (LXC `511`, `pve3`), and its full inventory lives on the tunnel page rather than here.

## Known gaps

The full member list of the AirVPN-routed `INTERNAL` group has never been exported, so the exact blast radius of the privacy egress is tribal knowledge. The NetBird peer inventory with owners and ACLs lives in the NetBird console rather than here, and the three road-warrior peers have all shown offline and may simply be dormant accounts worth pruning. None of this affects the tunnels themselves, which are healthy.
