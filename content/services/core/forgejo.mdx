Last synced with live infrastructure: **September 2026**.

All the code that runs this homelab — including the wiki you are reading — lives here. Forgejo is the private Git forge: it stores the repositories, and its runner on the compute node executes CI so builds never steal resources from the infrastructure node. The split is intentional and worth preserving. If the forge is down, nothing running breaks, but nothing new can ship either: no wiki redeploys, no CI. That makes Forgejo quiet but load-bearing.

## Components

| Kind | ID | Name | Host | Function |
|------|----|------|------|----------|
| LXC | `111` | `forgejo` | `pve1` | Git forge, `192.168.1.69` |
| LXC | `124` | `forgejo-runner` | `pve3` | CI runner |

## Placement

- The forge lives on `pve1` (infrastructure node).
- The runner lives on `pve3` (compute node). Keeping CI on `pve3` avoids loading the infra node with build work.

## Dependencies

- Forgejo uses a database. The PostgreSQL LXC (`112`) on `pve1` is the most likely backend, but the exact database wiring is not exported into this documentation.

## Storage

- Forge data and runner caches live on the LXC root disks (`local-lvm` on the respective hosts). Whether additional volumes from `pve1-storage` or `nas` are mounted is not captured here.

## Ingress

- Web UI at `git.cleeryy.cloud` → Caddy → `192.168.1.69:3000`. No SSO gate currently.

## Operational notes

- The runner depends on connectivity from `pve3` to the forge on `pve1`. A `pve1` outage halts CI even if `pve3` is up.
- The forge hosts the `homelab` wiki repository that Dokploy builds; a `pve1` outage blocks wiki redeploys (the running site is unaffected).

## Known gaps

The database wiring (which Postgres, which schema, where credentials live) is the one fact that would matter in a restore and is still unconfirmed. Runner labels and the per-repository usage are nice-to-have; the application-level backup story (beyond the guest-level PBS job) is the other item worth an hour before it is ever needed.
