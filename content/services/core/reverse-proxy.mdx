Last synced with live infrastructure: **September 2026**.

Every public hostname in the homelab ends its journey here. Caddy is the single front door: it holds the wildcard certificates, decides — by hostname — which internal service answers, and optionally demands a login via Authentik before proxying a single byte. That centralisation is what makes the rest of the setup manageable. Services never deal with certificates, ports 80/443 are forwarded exactly once at the firewall, and exposing something new is a small config file rather than a network change. If Caddy is down, everything behind it looks down too, even though all the apps are still healthy — always check here before restarting application containers.

## TLS

- Wildcard certificates via Cloudflare DNS-01 (`acme_dns cloudflare`), covering `cleeryy.cloud`, `*.cleeryy.cloud`, and `*.home.cleeryy.cloud`.
- Cloudflare proxy sits in front (public hostnames resolve to Cloudflare Anycast); OPNsense NAT-forwards 80/443 to `10.1.20.10`.
- Upstreams with self-signed certificates (Authentik, Wazuh, TrueNAS, n8n, Warpgate, PBS, Proxmox UIs) use `tls_insecure_skip_verify` on the Caddy side — TLS is still end-to-end, Caddy just does not validate the backend chain.

## Zones

Routes live in `/etc/caddy/sites/` on the Caddy host, split in two files trees imported by the main `Caddyfile`:

- **Public** (`sites/public/`, `*.cleeryy.cloud`): user services. Verified routes include `homelab` → `obiwan:3545` (this wiki), `dokploy` → `obiwan:3000`, `authentik` → `https://authentik:9443`, `code` → `code:8680` (behind Authentik `forward_auth`), `wazuh` → `https://wazuh:443`, `guacamole` → `apache-guacamole:8080`, `immich` → `immich:2283`, `chat` → `openwebui:8080`, `search` → `searxng:8888`, `dashboard` → `dynacat:8080`, `sure` → `sure:3000`, `affine` → `affine:3010`, `mc-dashboard` → `discopanel:8080`, `nextcloud` → `192.168.1.27:8080`, `n8n` → `https://192.168.1.13:443`, `jellyfin`/`jelly` → `192.168.1.31:8096`, `jellyseerr` → `192.168.1.31:5055`, `git` → `192.168.1.69:3000`, `matrix` → `192.168.1.67:8008`, `truenas` → `https://192.168.1.74`, `warpgate` → `https://warpgate:8888`. Unknown hosts get a `404`.
- **Private** (`sites/private/`, `*.home.cleeryy.cloud`): `pbs` → `https://pbs:8007`, `dns` (Technitium `:5380`), `proxmox`/`pve1`/`pve3` → `:8006`, `nas`, `adguard`, `ha`, plus service-internal routes.
- Caddy resolves service short names (`obiwan`, `authentik`, `code`, …) via internal DNS (Technitium, `.internal.cleeryy.cloud`).

## Adding a route

- [ ] Add a `<name>.caddy` file under `sites/public/` (or `sites/private/` for internal-only) following the existing `@name host … / handle @name { reverse_proxy … }` pattern.
- [ ] If the route must require login, add the Authentik `forward_auth` block (copy from `code.caddy`).
- [ ] `systemctl reload caddy` (validate via systemd env — a bare `caddy validate` fails on the Cloudflare token outside the service environment).
- [ ] Test from the Caddy host with a Host header, then over TLS, then from the public internet.
- [ ] Document the route on the service's wiki page.

## Failure impact

- If Caddy is down, all HTTPS-fronted services become unreachable from outside (and Cloudflare has nothing to talk to).
- OPNsense (`501` on `pve3`) is upstream of Caddy; its failure has broader impact (WAN + VLAN routing + VPN).
