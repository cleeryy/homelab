Last synced with live infrastructure: **September 2026**.

Every public hostname in the homelab ends its journey here. Caddy is the single front door: it holds the wildcard certificates, decides — by hostname — which internal service answers, and optionally demands a login via Authentik before proxying a single byte. That centralisation is what makes the rest of the setup manageable. Services never deal with certificates, ports 80/443 are forwarded exactly once at the firewall, and exposing something new is a small config file rather than a network change. If Caddy is down, everything behind it looks down too, even though all the apps are still healthy — always check here before restarting application containers.

## Placement

Caddy runs as a single LXC on `pve3` with the production address that OPNsense forwards ports 80 and 443 to. The previous Nginx-based ingress is out of the path: one VM is decommissioned and the other still runs on `pve1` with no confirmed ingress role, as tracked in the migration plan.

| Kind | ID | Name | Host | Function |
|------|----|------|------|----------|
| LXC | `2010` | `caddy` | `pve3` | Canonical reverse proxy, `10.1.20.10` |

Nginx Proxy Manager (VM `100`) has been decommissioned. `ubuntu-nginxrpm` (VM `105`) still runs on `pve1` but is no longer the ingress path; its remaining role is tracked in the [migration plan](/architecture/migration-plan).

## Status

Caddy is running as the canonical HTTPS ingress for both zones. Routes live as one file per hostname under `/etc/caddy/sites/`, imported by the main `Caddyfile`, with short service names resolved through internal DNS. Unknown hosts get a `404` rather than a default backend.

## TLS

Certificates are fully automatic through Cloudflare DNS-01, covering the apex and both wildcard trees. Public hostnames resolve to Cloudflare Anycast in front, with OPNsense forwarding 80 and 443 straight to Caddy. Backends that present self-signed certificates are still reached over TLS — Caddy simply skips validating their chain.

- Wildcard certificates via Cloudflare DNS-01 (`acme_dns cloudflare`), covering `cleeryy.cloud`, `*.cleeryy.cloud`, and `*.home.cleeryy.cloud`.
- Cloudflare proxy sits in front (public hostnames resolve to Cloudflare Anycast); OPNsense NAT-forwards 80/443 to `10.1.20.10`.
- Upstreams with self-signed certificates (Authentik, Wazuh, TrueNAS, n8n, Warpgate, PBS, Proxmox UIs) use `tls_insecure_skip_verify` on the Caddy side — TLS is still end-to-end, Caddy just does not validate the backend chain.

## Dependencies

Caddy depends on Technitium for short-name upstream resolution, on Cloudflare for DNS-01 issuance, and on OPNsense for the 80/443 forwards. If internal DNS fails, Caddy stays up but cannot route to short-name backends, which looks identical to every service being down.

## Adding a route

Exposing a new service is a small config change followed by a reload and a three-layer test. Copy the existing per-host pattern, add the Authentik block only when the route must require login, and remember that a bare `caddy validate` fails outside the service environment because the Cloudflare token only exists there.

- [ ] Add a `<name>.caddy` file under `sites/public/` (or `sites/private/` for internal-only) following the existing `@name host … / handle @name { reverse_proxy … }` pattern.
- [ ] If the route must require login, add the Authentik `forward_auth` block (copy from `code.caddy`).
- [ ] `systemctl reload caddy` (validate via systemd env — a bare `caddy validate` fails on the Cloudflare token outside the service environment).
- [ ] Test from the Caddy host with a Host header, then over TLS, then from the public internet.
- [ ] Document the route on the service's wiki page.

## Failure impact

If Caddy goes down, every HTTPS-fronted service becomes unreachable from outside even though the applications themselves are healthy, and Cloudflare has nothing to talk to. OPNsense (`501` on `pve3`) sits upstream of Caddy, so its failure is broader still: WAN plus VLAN routing plus VPN on top of the ingress outage.

## Known gaps

Two decisions remain open: whether public routes should require SSO by default or stay open under an explicit public list — most routes are currently open by inertia rather than by choice — and what to do with the leftover `ubuntu-nginxrpm` VM, which still runs with no confirmed role. Both are tracked in the migration plan; neither affects the Caddy path itself.
